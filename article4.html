🚨 When 90% Test Coverage Isn't Enough: A Lesson in Real Integration

📅 February 25, 2026 • 5 min read

🔧 The Setup

Teams have a strong quality engineering culture:

  • ✅ Acceptance tests with several dependent services mocked
  • ✅ Mocks aligned with the latest OpenAPI specs
  • ✅ ~90% automation coverage
  • ✅ Stable and reliable test suites
  • ✅ Countless successful releases

Which leads to:

  • 🟢 Green builds
  • ⚡ Faster pipelines
  • 💪 High confidence

Application deployed to a higher environment. And that's when things broke.

⚠️ The Surprise

Once deployed to a higher environment, the team encountered integration failures. The issue appeared only when the real services started communicating with each other.

The root cause? A subtle change in RestTemplate behaviour introduced during an upgrade.

What made it tricky:

  • Mocks were correct
  • OpenAPI contracts were up to date
  • Test coverage was strong

And yet, reality behaved differently.

📚 What to Learn Here

This wasn't a failure of automation. It was a reminder:

  • Mocked integrations validate contracts
  • Real integrations validate behaviour

Even perfectly aligned mocks cannot fully simulate:

  • Framework-level changes
  • Serialization/deserialization nuances
  • Header propagation differences
  • Timeout and retry behaviour
  • Hidden configuration shifts

In this case, the tech upgrade introduced a change that did not violate the API contract — but it altered runtime behaviour in a way mocks could not detect.

🧠 The QA Mindset Shift

This experience reinforces something critical:

Quality is not only about coverage. It's about risk awareness.

From a QA perspective, certain changes should automatically trigger additional thinking:

  • Framework upgrades
  • HTTP client changes
  • Serialization library changes
  • Security configuration updates
  • Infrastructure-level adjustments

These are not "just technical refactors." They are:

  • ⚠️ Integration risk multipliers

And they deserve:

  • Real environment validation before production

🧩 The Missing Layer

What most teams usually have:

  • Strong acceptance tests
  • Excellent contract validation
  • High automation confidence

What is often missing:

  • Early real-service integration verification

Not instead of mocks. But in addition to them.

Because:

  • Mocks are fast
  • Real integrations are truthful
  • Both matter

🎯 The Takeaway

  • Automation gives confidence
  • Integration gives assurance
  • Green builds do not always mean production readiness

Especially after:

  • Foundational changes
  • Framework upgrades
  • Core dependency updates

As QA engineers (and as teams), we must ask:

"What risks does this change introduce beyond the contract?"

Sometimes, the most valuable test is simply this:

Let the real services talk — before the customers do.
